# 智能盯盘模组（Watch Module）设计文档

> 版本：v1.0（设计稿）
> 依据：当前 `feature/copilot` 分支源码调研（模组/策略框架、Copilot 模块、前端模组管理页）
> 定位：在现有「模组 + 策略」体系之上，实现**可由自然语言动态定义的交易意图（WatchIntent）盯盘与自动执行**。

---

## 1. 需求与概念模型

### 1.1 交易意图（WatchIntent）六要素

用户在对话框里用自然语言表达的需求，被大模型翻译为一个结构化的交易意图：

| 要素 | 含义 | 落点 |
|---|---|---|
| **什么合约** | 盯盘标的（须在该模组绑定合约范围内） | `unifiedSymbol` |
| **什么周期** | 条件评估所基于的 K 线周期（M1~D1） | `interval` |
| **什么情况** | 触发条件，Groovy 布尔脚本，可引用实时价、K线、指标、模组持仓 | `triggerScript` |
| **什么价位/什么操作** | 触发后的动作：开/平、方向、手数、价格方式（市价/限价/超价），或仅提醒 | `action` |
| **何时失效** | 失效条件：到期时间 / 失效脚本 / 最大触发次数 | `invalidation` |
| **上下文** | 账户、行情订阅、指标预热 | 由**模组**承载（复用现有体系） |

示例（自然语言 → 结构化意图）：

> “螺纹钢 rb2601 跌破 5 分钟 MA20 且 MACD 死叉时，以对手价开空 1 手，今天下午 3 点前有效，只触发一次。”

```json
{
  "name": "rb2601 破位开空",
  "unifiedSymbol": "rb2601.SHFE",
  "interval": "M5",
  "triggerScript": "close(0) < ma(20).value(0) && macd(12,26,9).dif(0) < macd(12,26,9).dea(0) && macd(12,26,9).dif(1) >= macd(12,26,9).dea(1)",
  "action": { "type": "ORDER", "direction": "SELL", "offset": "OPEN", "volume": 1, "priceType": "OPPONENT" },
  "invalidation": { "expireAt": "2026-09-05T15:00:00", "maxTriggers": 1, "script": null }
}
```

### 1.2 与「策略 + 模组」的对照

| 维度 | 交易策略（现状） | 智能盯盘（本设计） |
|---|---|---|
| 逻辑来源 | 预编译 Java 类（`@StrategicComponent`） | **数据驱动的 Groovy 条件脚本**（运行时新增/删除，无需重启） |
| 条件数量 | 一个策略一套硬编码开平仓逻辑 | 一个模组内**动态维护多个意图** |
| 生命周期 | 随模组启停 | 每个意图独立：激活 → 触发/失效 → 归档 |
| 上下文（账户/合约/行情/指标预热） | 模组承载 | **完全复用模组承载** |
| 下单链路 | `ctx.submitOrderReq` → 风控 → ModuleAccount → 网关 | **同一条链路**，复用全部风控与状态机 |
| 交互界面 | 创建表单 + 运行时图表 | **对话框（自然语言）+ 意图列表 + 运行时面板** |
| 呈现方式 | 模组管理页 + 模组运行时页 | **独立的盯盘页，与模组管理/运行时页完全分离，互不出现** |

核心设计结论：**盯盘模组 = 一个独立模组类型（`ModuleType.WATCH`）+ 一个通用的 `WatchStrategy`（数据驱动的意图执行器）**。策略类本身是静态的，动态部分是作为"数据"存在数据库里的意图脚本。模组的生命周期、启停、预热、下单、持久化等**后端机制**全部复用；但**前端呈现完全独立**——盯盘模组不出现在原模组管理页，原模组管理页也不显示盯盘模组，避免用户混淆。

**模块归属**：

- `northstar-api`：意图领域模型（`WatchIntent` 等）与 `IWatchIntentRepository` 接口——因为 `WatchStrategy` 在 main 中但模型可能被 api 层引用，与 `ModuleDescription` 的处理方式一致。
- `northstar-main`：新增 `org.dromara.northstar.watch` 包（意图引擎、Groovy 沙箱、评估循环）+ `app/restful/WatchController` + `app/service/WatchChatService`、`WatchIntentService`。
- `northstar-copilot`：复用 `LlmProvider` / `LlmChatClientFactory` / `ToolLoader`，不改动。
- 新增依赖：**Groovy**（`org.apache.groovy:groovy:4.x`，加在 `northstar-main/pom.xml`）——项目当前无任何脚本引擎，这是唯一新增的基础设施。

## 3. 后端详细设计

### 3.1 领域模型（`northstar-api` → `org.dromara.northstar.common.model.watch`）

```java
// 交易意图
public record WatchIntent(
    String id,                    // UUID
    String moduleName,            // 所属盯盘模组
    String name,                  // 意图名称（LLM 生成，用户可改）
    String naturalLanguage,       // 用户原始自然语言描述（留痕）
    String unifiedSymbol,         // 合约
    Interval interval,            // 评估周期
    String triggerScript,         // 触发条件 Groovy 脚本（布尔表达式）
    WatchAction action,           // 触发动作
    WatchInvalidation invalidation, // 失效条件
    IntentStatus status,          // DRAFT/ACTIVE/TRIGGERED/EXPIRED/CANCELLED/FAILED
    int triggeredCount,
    long createdAt, long updatedAt,
    String lastMessage            // 最近一次触发/失效/失败的原因说明
) {}

public record WatchAction(
    ActionType type,        // ORDER（下单）/ NOTICE（仅提醒）
    Direction direction,    // BUY / SELL
    OffsetFlag offset,      // OPEN / CLOSE / CLOSE_TODAY...
    int volume,
    PriceType priceType,    // MARKET / LIMIT / OPPONENT / LAST
    Double limitPrice,      // priceType=LIMIT 时使用
    Integer plusTicks       // 超价跳数（复用模组 orderPlusTick 语义）
) {}

public record WatchInvalidation(
    Long expireAt,          // 到期时间戳（可空）
    Integer maxTriggers,    // 最大触发次数（默认1；可空表示不限直到其他失效条件命中）
    String script           // 失效条件脚本（可空，与触发脚本同一 Binding）
) {}

public enum IntentStatus { DRAFT, ACTIVE, TRIGGERED, EXPIRED, CANCELLED, FAILED }
```

状态机：

```
DRAFT（对话中起草，未确认）
  └─用户确认─▶ ACTIVE ─触发且达 maxTriggers─▶ TRIGGERED
                ├─expireAt 到期────────────▶ EXPIRED
                ├─失效脚本成立──────────────▶ EXPIRED
                ├─用户删除──────────────────▶ CANCELLED
                └─脚本编译/执行异常──────────▶ FAILED（不自动重试，需用户处理）
```

### 3.2 Groovy 脚本引擎（`org.dromara.northstar.watch.script`）

意图脚本运行在每个 Tick/Bar 上，且来自 LLM 生成（不可信代码），因此必须解决三件事：**沙箱、性能、熔断**。

**（1）沙箱**：`GroovyClassLoader` + `CompilerConfiguration.addCompilationCustomizers(new SecureASTCustomizer())`：

- 白名单接收者：`java.lang.Math`、`java.lang.Double/Integer/Long/Boolean/String`、`java.math.BigDecimal`、自定义 `WatchScriptBase`（脚本基类）；
- 禁止：`System`/`Runtime`/`Thread`/`File`/反射/`@Grab`/静态导入/自定义类定义；`setImportsBlacklist` + `setReceiversWhiteList`；
- 所有脚本继承 `WatchScriptBase extends Script`，把领域 API 以方法形式注入基类（而非自由变量），便于 AST 白名单控制。

**（2）Binding API**（`WatchScriptBase` 暴露给脚本的方法，也是写给 LLM 的"脚本 DSL 文档"，放入系统提示词）：

```groovy
// 行情（当前评估周期，step 0=当前bar, 1=上一根...）
close(step) / open(step) / high(step) / low(step) / volume(step) / turnover(step)
lastPrice()              // 最新 tick 价（onTick 评估时可用）
// 指标（惰性按需注册，见 3.4）
ma(n).value(step) / ema(n).value(step) / macd(f,s,m).dif(step)/.dea(step)/.hist(step)
boll(n,k).upper(step)/.mid(step)/.lower(step) / rsi(n).value(step) / atr(n).value(step)
// 模组上下文
position()               // 模组净持仓（>0 多 / <0 空 / 0 无）
available()              // 账户可用资金
barTime(step)            // K线时间戳
// 工具
crossUp(a0,a1,b0,b1) / crossDown(a0,a1,b0,b1)   // 金叉/死叉辅助
```

**（3）性能与熔断**：

- **编译缓存**：`Map<scriptHash, Class<? extends Script>>`，意图创建/激活时预编译（编译失败 → 意图置 `FAILED`，在对话框中反馈给 LLM/用户重写）；Tick 到来时零编译开销，仅 `newInstance()` + 执行。
- **执行隔离**：评估在 `ModuleHandler` 的事件线程上被间接触发，脚本不可控，因此把脚本执行提交到一个**盯盘专用单线程 Executor（带 500ms 超时）**；超时/异常 → 计数，连续 N 次失败将意图置 `FAILED` 并通知。事件线程只做"是否需要评估"的快速判断（意图列表按合约+周期索引）。
- **评估触发点选择**：`interval` 对应的 `onMergedBar`（收盘评估，适合"金叉/破位"类条件）与 `onTick`（实时价，适合"价格触及"类条件）。`WatchIntent` 增加隐含规则：脚本引用了 `lastPrice()` 的按 Tick 评估，其余按 Bar 收盘评估；由 LLM 生成时显式指定 `evalOn: TICK|BAR`。

### 3.3 WatchStrategy——数据驱动的通用盯盘策略

位置：`northstar-main` → `org.dromara.northstar.watch.WatchStrategy`，标注 `@StrategicComponent("智能盯盘")`，`type()` 返回新增的 `ModuleType.WATCH`（与原 `SPECULATION`/`ARBITRAGE` 区分；`ModuleService.loadModule` 中 `WATCH` 走与 `SPECULATION` 相同的 `ModuleContext` 分支）。用户通过盯盘页的简化创建表单创建盯盘模组（策略固定为它，不出现策略下拉框）。

```java
@StrategicComponent("智能盯盘")
public class WatchStrategy extends AbstractStrategy {
    public static class InitParams implements DynamicParams { /* 无需参数 */ }

    @Override protected void initIndicators() { /* 意图脚本引用的指标按需注册，此处为空 */ }

    @Override public void onMergedBar(Bar bar)   { intentEngine.evaluateOnBar(bar); }
    @Override public void onTick(Tick tick)      { intentEngine.evaluateOnTick(tick); }

    @Override public JSONObject getStoreObject() { /* 意图存 DB，不依赖 storeObject */ }
}
```

`IntentEngine`（Spring Bean，按模组名索引激活意图）：

```
class IntentEngine {
    Map<moduleName, Map<contract+interval+evalOn, List<WatchIntent>>> index;  // 激活意图索引

    evaluateOnBar(Bar bar):
        for intent in index[bar.contract][bar.interval][BAR]:
            if (!intent.invalidationSatisfied()) evaluate(triggerScript)  → 命中则 fire(intent)
            else expire(intent)

    fire(intent):
        1. 校验模组 enabled、意图 ACTIVE、triggeredCount < maxTriggers
        2. action.type == ORDER  → 组装 SubmitOrderReq → ctx.submitOrderReq()
           （走现有链路：DefaultOrderFilter 风控 → ModuleAccount 资金/持仓校验 → 状态机 → 网关）
           action.type == NOTICE → 仅发 NOTICE 事件
        3. triggeredCount++，持久化，SSE 推送 WATCH_INTENT 事件
        4. 达 maxTriggers → 状态置 TRIGGERED 并从索引移除
        5. 触发同时发 IMessageSender 通知（复用 EventNotificationHandler 的通知体系）
}
```

要点：

- **下单异常会触发框架"自动停用模组"**（`ModuleContext.submitOrderReq` 的既有行为）。盯盘场景下这过于敏感，设计上改为：意图下单失败仅将**该意图**置 `FAILED` 并通知，不拖累其他意图。实现上在 `WatchStrategy` 中对 `submitOrderReq` 包一层 try-catch 并记录，同时给盯盘模组 `setOrderRequestFilter` 一个稍宽松但仍有限额的过滤器。
- **撤单**：`LIMIT` 单未成交通知超时后由意图的 `invalidation.script` 或统一规则撤单（第一版可简单处理：收盘未成交自动撤单并通知）。

### 3.4 指标的按需注册与预热

这是盯盘与静态策略最大的差异：指标需求在意图创建时才出现。

- 脚本首次引用 `ma(20)` 等时（`WatchScriptBase` 的方法实现里）惰性调用 `ctx.registerIndicator(...)`；指标名按 `类型+参数+合约+周期` 生成唯一名，重复引用复用已有实例（查 `TimeFrameScopedRegistry`）。
- **预热**：新注册指标没有历史值（`isReady()==false`）。方案：意图激活流程中先收集脚本引用的指标集合 → 从 `IMarketDataRepository` 加载该合约最近 N 根对应周期 Bar（或直接复用 `ModuleDataLoader`+`KlineGenerator` 从 M1 合成）→ **只对新注册的指标实例**回放更新（直接调 `indicator.update(...)`，不走模组主事件链，避免重复喂给已有指标与策略）。预热完成后意图才进入 `ACTIVE`。
- 指标可视化的副产品：注册的指标自动出现在模组运行时图表上（`visible=true`），用户能看到"大模型在盯什么线"。

### 3.5 对话子系统（`WatchChatService`）

复用 `northstar-copilot` 基础设施：`LlmChatClientFactory.create(provider)` + Spring AI `MessageChatMemoryAdvisor`（会话 ID = `watch:{moduleName}`，窗口 20 条；**第一版内存会话即可**，重启后对话清空但意图在 DB 中不丢）。

**系统提示词**（关键资产）包含：

1. 角色设定与交互协议：先理解需求 → 反问补全缺失要素（合约/周期/价位/失效条件）→ 输出意图草稿 → 等用户确认；
2. 当前模组上下文：绑定账户、绑定合约列表（`ctx.bindedContracts()`）、默认手数、当前持仓与最新价（作为工具调用实时获取，而非塞死上下文）；
3. 脚本 DSL 文档（3.2 的 Binding API 全量说明 + 3~5 个 few-shot 示例）；
4. 输出协议：意图草稿以固定 JSON Schema 输出，包裹在 ` ```intent ` 代码块中。

**确认流（两阶段，工具不直接落库激活）**：

```
用户: "rb跌破5分钟MA20开空1手，收盘前有效"
 LLM: (调用工具 get_latest_price / get_position 补全上下文)
 LLM: 回复确认话术 + ```intent {DRAFT JSON}```
前端: 解析 intent 块 → 在意图列表区渲染"待确认草稿卡片"（[确认激活] [放弃]）
用户: 点[确认激活] → POST /northstar/watch/intent → 服务端编译校验脚本+预热指标 → ACTIVE
```

- 草稿阶段服务端做**静态校验**：合约必须属于模组绑定合约、脚本可编译、动作要素齐全、失效条件至少一项（防止"永远有效"的失控意图）。
- 可选增强（二期）：激活前用最近 N 周历史 Bar 对 `triggerScript` 做**干跑（dry-run）**，回复用户"该条件过去 5 个交易日会触发 2 次"，帮助用户发现条件过松/过紧。

**LLM 工具**（`@CopilotTool` 类，`ToolLoader.load("org.dromara.northstar")` 扫描；注意 ToolLoader 要求无参构造，需要 Spring Bean 的工具改为在 `WatchChatService` 中显式 `new` 注册而非扫描）：

| 工具 | 说明 |
|---|---|
| `get_latest_price(symbol)` | 最新价（`MarketCenter`/`IMarketDataRepository`） |
| `get_position(moduleName)` | 模组持仓与状态 |
| `list_watch_intents(moduleName)` | 当前意图列表 |
| `validate_intent_script(script)` | 编译+沙箱校验，返回错误信息供 LLM 自我修正 |
| `draft_watch_intent(json)` | 生成草稿（仅暂存并返回草稿 ID，不激活） |

### 3.6 持久化

新增一张表，沿用项目"整存整取 JSON"的既有风格（参考 `ModuleDescriptionDO`）：

```java
@Entity @Table(name = "WATCH_INTENT")
public class WatchIntentDO {
    @Id private String id;            // 意图UUID
    private String moduleName;        // 索引：按模组查询
    private String status;            // 索引：恢复时只加载 ACTIVE
    @Lob private String dataStr;      // WatchIntent 完整 JSON
}
```

- `northstar-api`：`IWatchIntentRepository`（`save/findById/findByModule/deleteById/findActiveByModule`）。
- `northstar-main`：`data/jdbc` 下 `WatchIntentDO` + `WatchIntentRepository`（JPA）+ `WatchIntentRepoAdapter`，在 `RepositoryConfig` 注册 Bean。
- **重启恢复**：`ModuleService.loadModule` 装配 `WatchStrategy` 后，`IntentEngine` 从 DB 加载该模组 `ACTIVE` 意图 → 重建脚本编译缓存与指标 → 预热 → 入索引。对话历史不恢复（内存会话），意图列表不丢。

### 3.7 REST API（`WatchController`，基础路径 `/northstar/watch`，全部走既有 CSRF 拦截）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/northstar/watch/chat` | 对话（`SseEmitter` 流式返回 LLM 输出；入参：moduleName + message） |
| GET | `/northstar/watch/intents?moduleName=` | 意图列表（含 DRAFT/ACTIVE/TRIGGERED/EXPIRED） |
| POST | `/northstar/watch/intent` | 确认激活草稿（编译校验+预热） |
| PUT | `/northstar/watch/intent/{id}` | 编辑（仅 DRAFT/FAILED 可编辑，编辑后重新校验） |
| DELETE | `/northstar/watch/intent/{id}` | 删除（→ CANCELLED） |
| POST | `/northstar/watch/intent/dryrun` | （二期）历史干跑，返回触发时间点列表 |

**SSE 推送**：`SseBroadcastHandler` 增加事件类型 `WATCH_INTENT`（JSON：意图全量字段），意图状态每次变更时推送，前端意图列表免轮询实时刷新。对话流式输出走 `POST /chat` 自己的 `SseEmitter`（不复用 `/sse/stream`，因为后者是全局广播且 GET）。

## 4. 前端设计（northstar-monitor-next）

### 4.1 页面与路由

**呈现隔离原则**：盯盘模组与原模组管理页、模组运行时页**完全分离、独立呈现**，互不出现，减少用户困惑：

- 盯盘模组**不出现在** `/module/mgmt`（模组管理页）——该页查询模组列表后按 `type != WATCH` 过滤；
- 普通模组**不出现在** `/watch`（盯盘页）——盯盘页只列出 `type == WATCH` 的模组；
- 盯盘模组**不使用** `ModuleRuntimeDesktop/Mobile`（原模组运行时页）——其运行时视图就是盯盘页右侧的运行时面板区（见下）；
- 后端 `/northstar/module/**` 接口不变（对后端而言盯盘模组就是普通模组），过滤只发生在前端呈现层与各自的查询参数上；
- 盯盘页自带**简化版创建入口**：表单仅需名称、账户、合约、预热周期等，`strategySetting` 固定为 `WatchStrategy`、`type` 固定为 `WATCH`，不让用户做策略选择。

新增 `src/router/modules/watch.ts`（自动注册）：

| 路径 | 组件 | 说明 |
|---|---|---|
| `/watch` | `src/views/watch/index.vue` | 智能盯盘主页（菜单"智能盯盘"） |

**盯盘页 = 现有模组运行时页的超集**：在保留模组运行时的「K线图表、账户/持仓、绩效统计、成交记录」全部能力之上，增加「对话框 + 意图列表」两个盯盘面板块。这样用户在一个页面内既能表达/管理交易意图，又能持续观察模组运行状况。

布局（桌面端；移动端降级为 Tab 切换，复用 `deviceDetection()` 双端模式）：

```
┌───────────────────────────────────────────────────────────────────────┐
│ header: 盯盘模组选择器（仅列出 type=WATCH 的模组） + 新建盯盘模组（简化表单）   │
├──────────────┬────────────────────────────────────────────────────────┤
│              │  ┌──────────────────────────────────────────────────┐  │
│  对话面板      │  │  运行时K线图（周期切换/指标线/画线，叠加意图触发价位线）│  │
│  WatchChat   │  ├──────────────────────┬───────────────────────────┤  │
│  .vue        │  │  账户/持仓面板          │  绩效统计面板               │  │
│  （SSE流式）   │  │  （复用 ModuleAccount）│  （权益/胜率/回撤/年化等）    │  │
│              │  ├──────────────────────┴───────────────────────────┤  │
│              │  │  意图列表（el-table：状态tag/触发次数/[确认][删除]）  │  │
│              │  │  + 成交记录（el-table，可切换Tab，支持导出CSV）      │  │
│              │  └──────────────────────────────────────────────────┘  │
└──────────────┴────────────────────────────────────────────────────────┘
```

| 板块 | 复用来源 | 数据来源（后端接口全部已存在，无需新增） |
|---|---|---|
| 运行时 K 线图 | 参考 `ModuleRuntimeDesktop.vue` 的 `klinecharts` 用法 + `makeTemplate` 指标模板 | `GET /northstar/module/{name}/chart`（各周期 bar+指标线）+ SSE `BAR` 实时推送 |
| 账户/持仓 | 直接复用组件 `src/views/module/components/ModuleAccount.vue` | `GET /northstar/module/{name}/rt` + SSE `ACCOUNT`/`POSITION` |
| 绩效统计 | 参考 `ModuleRuntimeDesktop.vue` 的统计区 | `GET /northstar/module/{name}/rt`（`ModuleRuntimeVO`：权益/胜率/最大回撤/年化等） |
| 成交记录 | 参考 `ModuleRuntimeDesktop.vue` 的成交表与 CSV 导出 | `GET /northstar/module/{name}/deals` |
| 对话框 / 意图列表 | **新增** | 3.7 节新增接口 + SSE `WATCH_INTENT` |

实现建议：把 `ModuleRuntimeDesktop.vue` 中图表、绩效、成交记录三块抽为可复用组件（或在盯盘页内直接以同法实现），盯盘页按当前选中的盯盘模组名取数——对后端而言，盯盘模组就是普通模组，现有 `/northstar/module/**` 接口原样可用。

### 4.2 关键实现点

- **API 层**：`src/api/watch.ts`（`http.request`）。对话例外：`fetch("/northstar/watch/chat", { method:"POST", headers:{ CSRF_token: getToken() } })` + `ReadableStream` 逐段解析 SSE——因为 `EventSource` 不支持 POST/自定义头。
- **Store**：`src/store/modules/watch.ts`——`intents`（按当前模组）、`chatMessages`、`streaming` 状态；在 `connectionStore.ts` 注册 `WATCH_INTENT` 事件监听同步意图列表。
- **类型**：扩展 `types/northstar.d.ts`（`WatchIntent`、`WatchAction` 等；已有 `ChatCompletionDTO` 可复用）。
- **意图确认交互**：解析助手消息中的 ` ```intent ` 块 → 意图列表顶部的草稿卡片（结构化展示六要素 + 脚本可展开查看 + 确认/放弃按钮）。
- **K 线联动**：意图列表点击行 → 图表切换对应合约+周期，触发价位画水平线（复用画线能力）；意图脚本注册的指标自动出现在图表指标线中（后端 `visible=true`，见 3.4）。
- **持仓/绩效刷新**：与模组管理页一致，无需轮询——`connectionStore` 的 SSE `ACCOUNT`/`POSITION`/`MODULES` 事件自动驱动；绩效区在进入页面时调一次 `moduleApi.moduleRuntime` 后靠事件增量更新。

## 5. 关键流程

### 5.1 意图创建（对话 → 确认 → 激活）

```
用户 ─自然语言─▶ WatchChatService ─▶ LLM(系统提示词+工具+会话记忆)
                                        │ 反问/补全，直至要素齐全
                                        ▼
                          回复确认话术 + intent JSON 草稿
                                        ▼
前端渲染草稿卡片 ─用户确认─▶ POST /intent
                                        ▼
        服务端：静态校验 → Groovy 沙箱预编译 → 指标按需注册+历史预热 → ACTIVE 落库
                                        ▼
                        SSE(WATCH_INTENT) 广播 → 列表实时出现
```

### 5.2 意图触发

```
行情网关 ─Tick/Bar─▶ Disruptor ─▶ ModuleHandler ─▶ TradeModule(合约过滤)
  ─▶ WatchStrategy.onTick/onMergedBar ─▶ IntentEngine
      ├─ 失效检查（到期/失效脚本/次数）→ EXPIRED + 通知
      └─ 触发脚本求值(沙箱+超时) 命中
            ├─ ORDER: ctx.submitOrderReq → 风控 → ModuleAccount → 网关
            │         成交回报 → Order/Trade 事件 → 既有通知与 SSE 链路
            ├─ NOTICE: NOTICE 事件 → EventNotificationHandler（消息推送）
            └─ 计数+落库+SSE 推送；达上限 → TRIGGERED 归档
```

### 5.3 失效与删除

- 到期/失效脚本：由评估循环顺带检测（无独立定时器；另加一个每分钟的兜底 `@Scheduled` 扫描处理无行情时段的到期）。
- 用户删除：仅移除索引与置 `CANCELLED`，保留 DB 记录可追溯。

## 6. 安全与风控

| 风险 | 对策 |
|---|---|
| LLM 生成恶意/失控脚本 | SecureASTCustomizer 白名单沙箱；禁 IO/反射/线程；脚本仅布尔表达式 |
| 脚本死循环/耗时 | 专用线程池执行 + 500ms 超时 + 连续失败熔断置 FAILED |
| 条件过宽导致刷单 | 复用 `DefaultOrderFilter` 日内限额；意图级 `maxTriggers` 必填校验（默认 1）；`ModuleStateMachine` 下单中禁重复下单 |
| LLM 误操作直接下单 | **两阶段确认**：工具只能起草 DRAFT，激活必须用户点击；下单类意图前端二次确认弹窗 |
| 永远有效的意图 | 激活校验：失效条件三要素至少一项（到期时间/失效脚本/触发次数） |
| 接口安全 | 全部走既有 `AuthCheckerInterceptor` CSRF 体系 |
| LLM 平台限流 | 429 指数退避重试（30/60/90s），失败在对话框提示降级（可切换 `LlmProvider`） |

## 7. 实施路线（建议分期）

**一期（MVP）**
1. `northstar-main/pom.xml` 引入 Groovy；实现 `WatchScriptBase` + 沙箱 + 编译缓存（含单测）；
2. `WatchIntent` 模型 + `IWatchIntentRepository` + JDBC 落地；
3. `WatchStrategy` + `IntentEngine`（仅 NOTICE 动作 + ORDER 市价/对手价）；
4. `WatchController`（intents CRUD，对话暂不接）；
5. 前端：意图列表页 + 手工创建意图表单（绕过 LLM，先打通全链路）。

**二期（对话接入）**
6. `WatchChatService` + 系统提示词 + 工具集 + POST SSE 对话接口；
7. 前端对话面板 + 草稿确认卡片 + K 线联动；
8. 重启恢复、每分钟到期兜底扫描、消息通知接入。

**三期（增强）**
9. 历史干跑（dry-run）验证意图；
10. 对话历史持久化（实现 `ChatMemoryRepository` JDBC 版）；
11. PLAYBACK 用途复用：意图在回放模组中验证（回测盯盘条件）。

## 8. 开放问题

1. ~~模组类型~~（已决策）：新增 `ModuleType.WATCH` 枚举值，盯盘模组与普通模组以类型明确区分。涉及改动：`ModuleService.loadModule` 的上下文选择分支（`WATCH → ModuleContext`，与 SPECULATION 相同）、`WatchStrategy.type()` 返回 `WATCH`、前端两个页面的过滤逻辑。改动范围小且明确。
2. **多合约意图**：一个意图只盯一个合约（保持简单）；跨合约套利类条件用两个意图或后续扩展。
3. **平仓意图与持仓来源**：盯盘模组平自己模组持仓走现有链路；若想平"模组外手工持仓"，需要 `offset=CLOSE` 直接路由到账户——建议一期不支持，仅支持模组内持仓。
4. **LLM 选择**：对话框顶部提供平台下拉（`LlmProvider` 枚举 + `isAvailable()` 过滤），默认取第一个可用平台。
