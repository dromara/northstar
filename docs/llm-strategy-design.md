# 智能策略（LLM Strategy）功能设计

> 状态：设计稿（第 4 版，含 PoC 定位与成功指标、双模式交易意图、策略版本化、运行护栏）
> 关联模块：`northstar-copilot`、`northstar-api`、`northstar-main`、`northstar-monitor-next`

## 1. 背景与痛点

用户把策略思路转化为代码，是 Northstar 使用门槛最高的环节：

- **规则穷举路线**：行情千变万化，用 if-else 穷举交易规则，编码难度高、复杂度失控、可维护性差；
- **数据拟合路线**（如强化学习）：算法门槛极高，几乎只有开发者本人能驾驭。

**破局思路**：借助大模型的逻辑判断力，把复杂条件关系用自然语言描述。平台提供四个框架——策略思路描述框架、工具定义框架、正例与反例框架、可解释框架。

**阶段定位**：本功能当前处于 **PoC（概念验证）阶段**。核心假设——"LLM 的盘中决策质量值得用户托付真金白银"——尚无任何必然成功的依据，必须用数据说话。因此 PoC 阶段的一切设计服务于一个目标：**以最低成本产出可信的验证数据（用例通过率、调用成本、决策质量），支撑 go/no-go 决策**。

## 2. 需求推导：从痛点到功能点

### 2.0 PoC 成功指标

| 指标 | 定义 | 用途 |
|---|---|---|
| **策略定稿判据** | **测试用例通过率**：策略在历史时段用例中预演，用户逐条确认预演意图，通过比例 ≥ 预设阈值（默认 80%，可配置）方可定稿 | 定稿是挂载运行的前置条件，也是 PoC 的核心验证动作 |
| **单日 LLM 调用成本** | 按策略/按日统计 token 消耗与折算金额 | 回答"这个功能烧多少钱"，成本失控即熔断 |
| **意图执行失败率** | 校验失败、执行异常、LLM 超时/拒答占全部意图产出的比例 | 衡量引擎可靠性与 Prompt 质量 |
| **影子模式决策质量** | dryRun 意图的虚拟盈亏、胜率、盈亏比 | 回答"AI 的决策是否具备正期望"，go/no-go 的核心依据 |

### 2.1 用户画像与核心场景

目标用户是**有交易经验但不会（或不愿）写代码的交易者**。其核心动线：

```
【创建期：人机协作】
写下策略想法（自然语言） → 与大模型多轮对话打磨规则，直到双方理解一致
→ 选择若干历史时段作为测试用例，预演大模型在实盘情境下的反应
→ 用例通过率达标 → 策略定稿；不达标则继续打磨
【运行期：全自动 + 护栏】
挂载合约运行（先影子模式）→ AI 全自动决策，运行过程不与用户交流
→ 触发熔断条件时自动停用模组并通知用户人工接管
→ 用户在复盘界面对意图记录评分/批注 → 案例反哺后续决策
→ 确认靠谱后小仓位实盘 → 复盘时完整重现每次意图
```

### 2.3 关键取舍（推导结论）

1. **LLM 策略实现为特殊的 `TradeStrategy`（`LlmDrivenStrategy`）**，而不是独立子系统。模组运行时（事件分发、指标更新、状态机、风控、账户路由、回测/模拟/实盘三态复用）全部免费获得，符合"策略只面向 `IModuleStrategyContext` 编程"的现有架构哲学。
2. **自然语言规则本身就是"程序"，平台不生成任何固定代码**。用户写下的规则不会被翻译成 Java 代码或静态指令集；盘中每个决策时点，程序把规则原文交给大模型，由大模型**实时调用工具完成计算、实时进行逻辑判断**，产出当次决策。规则不可原地修改，迭代走版本化，参考第 9 点。
3. **交易意图（TradeIntent）分为两类，策略创建时由用户二选一，一个策略实例只使用一种模式，两者分开评分、互不混评**：
   - **半自动意图**：LLM 产出封闭枚举的简单动作——开多/开空/平多/平空/加仓/减仓/观望（HOLD），带数量参数。持仓生命周期全程依赖 LLM 后续决策（开仓后需 LLM 再决策平仓）。**评分单元：逐笔，平仓盈亏归属到开仓意图。**
   - **全自动意图**：LLM 一次性产出完整交易计划——入场点位 + 止盈点位 + 止损点位（+数量），提交后由平台托管执行（复用 `PlannedTradeHandler` 计划交易机制）。**评分单元：整笔计划从入场到止盈/止损出场的最终盈亏。**
   - 划分收益：① 评分标准各自明确，避免两种决策模式混评导致打分失真；② 全自动意图的止盈止损由平台保证执行，**LLM 故障/超时不会导致"开了仓无法平仓"的裸奔敞口**；③ 意图仍是 LLM 影响真实交易的唯一通道，是执行校验、持久化、打分、复盘统一的基本单元。
4. **创建期可交互、运行期全自动但有护栏**。创建阶段，用户可与大模型多轮对话打磨规则（F2），并必须通过测试用例预演（F13）达到通过率阈值方可定稿；一旦挂载运行，策略自动执行、不与用户交流——但熔断条件触发时自动停用模组并通知用户人工接管（F14）。运行期日常唯一的人机交互，是事后在复盘界面对意图记录评分（F9）。
5. **决策粒度由特定事件驱动**，不在 TICK 与 BAR 级触发（成本与延迟均不可行）。
6. **dryRun 影子模式默认开启**：新策略只记录意图与虚拟盈亏，人工确认后才放开真实执行。
7. **LLM 不绕过任何现有风控**：意图执行时仍走 `OrderRequestFilter → ModuleAccount` 全链路；人工接管复用模组启停设计，不引入旁路控制。
8. **不做模型训练**：正反例通过 few-shot 提示词注入生效，不微调模型。
9. **策略规则不可原地修改，但策略支持版本化**：策略 = **不可变的规则快照（版本）+ 可变的管理外壳**（名称、合约绑定、启停、版本切换）。修改规则即生成新版本（v1/v2/…），各版本独立积累用例通过率与意图评分，并提供版本间对比视图。这样既保证"历史评分始终对应同一份规则"的统计有效性，又不惩罚用户的正常迭代。
10. **支持实盘模式与回放模式**：在实盘模式下，与大模型的交互异步进行，不影响 TICK/BAR 数据的线程；在回放模式下，与大模型的交互同步进行，以确保时间先后的准确性。
11. **运行护栏复用而非新建**：熔断触发 = 调用现有模组停用能力（复用启停状态机与状态一致性保证），风控阈值判断挂在现有 `OrderRequestFilter` 链路；接管动作就是用户在前端对模组执行启停/手工平仓，平台只增加"自动触发 + 通知"，不新增并行控制体系。

### 2.4 里程碑划分

| 里程碑 | 目标 | 包含功能 | Go/No-Go 判据 |
|---|---|---|---|
| **M1：PoC 验证** | 影子模式闭环，产出验证数据 | F1（简化版）、F3、F4、F5、F7、F13、F15（F14 基础接管） | 用例通过率可达阈值；单日调用成本在预算内；意图失败率可接受；dryRun 意图统计呈正期望 → 否则终止或转向 |
| **M2：信任链** | 复盘、反哺、护栏完整化 | F2、F8、F9、F10、F11、F14（阈值熔断） | 用户愿意基于复盘数据放开小仓实盘 |
| **M3：小仓实盘** | 真实资金验证 | F12、F6，放开真实执行 | 实盘结果与影子模式无显著劣化 |
